# Табличные привилегии клиента: замер 18.09.2026

Найдено при проверке миграции 34 сразу после выката. Документ существует,
чтобы завтрашняя работа началась с фактов, а не с повторного открытия.

## Что измерено

Запросы под ключом `anon` и под обычной учёткой (`authenticated`). Все
подобраны так, чтобы не менять ни одной строки: `id` заведомо несуществующий,
поэтому `DELETE` и `PATCH` попадают в ноль строк.

| Запрос | Ответ | Что означает |
|---|---|---|
| `GET /tool_demands` | `200 []` | право SELECT **есть**, строк не отдаёт RLS |
| `PATCH /tool_demands` | `204` | право UPDATE **есть** |
| `DELETE /tool_demands` | `204` | право DELETE **есть** |
| `DELETE /bookings` | `204` | право DELETE **есть** |
| `DELETE /users` | `204` | право DELETE **есть** |
| `DELETE /items` | `204` | право DELETE есть — и здесь оно законно (владелец удаляет своё) |
| `DELETE /reviews` | `204` | право DELETE **есть** |

Для сравнения, отказ выглядит иначе — так отвечает закрытая колонка:

```
GET /users?select=phone  →  401  42501  permission denied for table users
```

## Механизм

В схеме `public` у Supabase стоит

```sql
alter default privileges in schema public grant all on tables to anon, authenticated;
```

Поэтому **базовое состояние новой таблицы — не «прав нет», а «права есть
все»**. Ни одной строки об этом в миграциях проекта нет, и по ним состояние
выглядит противоположным.

Отсюда прямое следствие для автора миграции: у новой таблицы первым
оператором идёт `revoke all … from anon, authenticated`, и только потом
нужный `grant`. Без этого «сузил права» — иллюзия. Ровно так вышло с
`tool_demands` в миграции 34; исправлено миграцией 36.

## Чем это опасно, если RLS и так держит

Тем же, чем миграция 27 была опасна для `bookings`: защита стоит на одном
рубеже вместо двух, и стоит молча.

Пока политики на чтение нет, `SELECT` не отдаёт строк. Но тот, кто завтра
добавит узкую политику — «свои заявки видны автору», — получит вместе с ней
полный табличный `SELECT`, и красным при этом не станет ничего: ни тест, ни
сборка, ни гейт.

## Что уже закрыто

* `public.bookings` — `INSERT`, `UPDATE` сняты миграцией 33. `DELETE`
  **остаётся открытым**.
* `public.tool_demands` — миграция 36: `revoke all`, затем `grant insert`.
* `public.admin_audit_log` — миграция 25 сняла всё сразу, это образец.

## Что открыто и требует отдельной работы

Не сделано сегодня НАМЕРЕННО: массовый `revoke` затрагивает весь клиентский
путь сразу, и ошибка в одной строке ломает продукт целиком. Перед каждой
снимаемой привилегией нужно назвать место в коде, которое ею не пользуется.

| Таблица | Клиенту нужно | Похоже, лишнее |
|---|---|---|
| `bookings` | `SELECT` | `DELETE` |
| `users` | `SELECT` по колонкам, `UPDATE` по колонкам (миграция 17) | `INSERT`, `DELETE` |
| `reviews` | `SELECT`, `INSERT` | `UPDATE`, `DELETE` |
| `booking_messages` | `SELECT`, `INSERT` (миграция 11) | `UPDATE`, `DELETE` |
| `booking_photos` | `SELECT`, `INSERT`, `DELETE` (миграция 11) | `UPDATE` |
| `payments` | `SELECT` | остальное |
| `item_blackouts` | всё четыре (миграция 22, владелец правит перерывы) | — |
| `items` | всё четыре (миграция 27) | — |

Столбец «похоже, лишнее» — гипотеза, а не приговор: каждую строку перед
снятием сверить с кодом. Замеров по `INSERT`/`UPDATE` для этих таблиц НЕ
делалось намеренно — это тридцать с лишним запросов к проду подряд, а такой
всплеск однажды уже ронял его.

## Чего не видит гейт

`scripts/check-migration-grants.mjs` проигрывает **только написанное в
миграциях**. Умолчаний Supabase в них нет, поэтому таблицу, которой никто
явно ничего не снимал, он считает чистой. Это записано в его шапке.

Сделать гейт правдивым можно: засеивать поднадзорные таблицы полным набором
прав (настоящее базовое состояние) и считать нарушением всё, что не снято
явно. Тогда он сразу покажет строки из таблицы выше — и потребует либо
снятия, либо явной заморозки в списке-храповике, как в
`db-access-allowlist.json`. Это следующая работа, не сегодняшняя.

# Что сделано 19.09.2026

## 1. Сторож научился видеть умолчания

`scripts/check-migration-grants.mjs` теперь ЗАСЕИВАЕТ каждую встреченную
`create table` в схеме `public` полным набором прав для `anon` и
`authenticated` — тем состоянием, которое создаёт умолчание Supabase.

Проверка модели: итог совпал со ВСЕМИ живыми замерами из таблицы выше —
`bookings`, `users`, `reviews` отдают `DELETE`; `users` не отдаёт табличный
`SELECT`; `tool_demands` держит только `INSERT`. Модель воспроизводит живую
базу, а не намерение миграций.

## 2. Нашлась вторая слепая зона — файл, который не применяется

`supabase migration list` говорит вслух на каждом запуске:

```
Skipping migration add_events_table.sql...
(file name must match pattern "<timestamp>_name.sql")
```

То есть `public.events` **не создаётся миграциями никогда**. На проде
таблица при этом ЕСТЬ — её завели руками:

```
GET /rest/v1/events?select=id&limit=1  →  200 []   (ключ anon, 19.09)
```

Сторож же читал этот файл и отчитывался о привилегиях таблицы, которой в
базе из миграций не существует. Теперь он пропускает такие файлы так же,
как CLI, и **называет их вслух** отдельным блоком: файл, который выглядит
миграцией и не исполняется, опаснее отсутствующего — по нему судят о базе.

⚠️ Открыто: `public.events` из миграций не воспроизводится. В чистой базе
её не будет. Решать — удалять файл или давать ему метку времени (и тем
самым заводить таблицу на проде) — не мне.

## 3. Миграция 37: снято то, что доказано ненужным

| Что снято | Откуда уверенность |
|---|---|
| `TRUNCATE`, `REFERENCES`, `TRIGGER` на девяти таблицах | PostgREST не выражает ни одну из трёх: нет ни маршрута, ни глагола. Класс, а не набор случаев |
| `users`: `INSERT` | строку заводит триггер `handle_new_user` на `auth.users` (миграция 31, SECURITY DEFINER) |
| `users`: `DELETE` | удаление учётки идёт edge-функцией `delete-account` под `service_role` |
| `bookings`: `DELETE` | `.delete()` по bookings нет нигде в `src/hooks/mutations`; брони вещи уходят КАСКАДОМ по FK, а каскад привилегию текущей роли на дочерней таблице не спрашивает |
| `events`: всё, под `to_regclass` | продукт таблицей не пользуется: `from('events')` нет ни в `src`, ни в edge-функциях |

Колоночные гранты на `users` (миграции 07, 14, 17) НЕ затронуты: они живут
отдельно от табличных.

## 4. Храповик на всю поверхность

`scripts/migration-grants-allowlist.json` замораживает явь поимённо — восемь
таблиц, обе клиентские роли, с полем `why` у каждой. Сторож падает на любом
отличии **в обе стороны**: появилась привилегия, которой нет в списке, —
красный; привилегию сняли, а строка осталась — тоже красный.

Сверка в обе стороны не формальность: список, из которого не убирают
снятое, за полгода превращается в художественное произведение, и врать
начинает он, а не миграции.

## Что осталось долгом

Строки с пометкой «НЕ СВЕРЕНО» в `why`:

* `reviews` — `UPDATE`, `DELETE`
* `booking_messages` — `UPDATE`, `DELETE`
* `booking_photos` — `UPDATE`
* `payments` — всё, кроме `SELECT`

У `reviews` и `booking_messages` политики на запись ЕСТЬ, и снимать
табличное право, не прочитав политику, значит менять поведение вслепую.
Снимать по одной таблице, с названным местом в коде.
